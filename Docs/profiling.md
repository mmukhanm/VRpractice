# Профилирование — этапы 1–6

**Андижан Мухаммед · Unity 6000.6.0f1 · сцена Profiling_Андижан**

Это реализация инструментов и воспроизводимый протокол измерений. В облаке нет Unity Editor: сцена создаётся редакторским генератором при открытии проекта, а не запущена здесь. Реальные .data, FPS/CPU/GPU/GC, скриншоты, результат lightmapping и Windows .exe не заявляются готовыми. Excel-шаблон содержит пустые измерения; 13,9 мс — заданный бюджет, а не результат.

## Подготовка и файлы

1. Откройте проект в Unity 6000.6.0f1. Дождитесь импорта закреплённых пакетов; добавлен **Profile Analyzer 1.4.2**.
2. Если сцен работы 6 ещё нет: **VR Practice → Build workshop scenes**. Затем **VR Practice → Profiling → Create or rebuild scene** и **Validate scene**. Существующая Profiling_Андижан перед явной пересборкой копируется вместе с папкой освещения в `Artifacts/SceneBackups`. Генератор не переносит ваши ручные правки в новую сцену.
3. Откройте `Assets/Scenes/Profiling_Андижан.unity`, нажмите Play. CP1 — вход; CP2 — центр; CP3 — близкий обзор самого подробного кресла, стола, радио и автомобиля. Направление каждой метки задаёт горизонтальное направление камеры, с компенсацией локального HMD-смещения. Метки редактируются в Inspector, если ваша сцена отличается.
4. Включите **Stats** кнопкой в Game View. FrameTimeMeter использует скользящее окно 120 кадров и показывает frame mean/max и FPS. Сравнивайте на устойчивой нагрузке после нескольких секунд, при одинаковом размере Game View. Frame time по unscaledDeltaTime включает ожидания; это не то же самое, что активная работа CPU Main/Render Thread. Значения Stats и таблички здесь не сверены фактическим запуском.
5. World Space Canvas следует за взглядом на высоте камеры на расстоянии 2 м. Во время записи его текст заморожен; обновления/строки интерфейса не должны вносить регулярный GC в интервал. Legacy HUD отключён только в копии сцены.

### Управление

| Клавиша | Действие |
|---|---|
| 1 / 2 / 3 | Перенос XR Origin в CP1 / CP2 / CP3 |
| N | Цикл N: 0 → 100 → 250 → 500 → 1000 → 2000 → 0 |
| 0 | Нагрузочный режим с N=0 |
| M | Baseline → SRPBatcher → GPUInstancing → LOD → Baseline |
| B / G | 500 объектов с точным BadBehaviour / оптимизированным GoodBehaviour |
| V | То же число объектов без Bad/Good |
| P / O | 300 падающих объектов Convex MeshCollider / BoxCollider; запись начинается автоматически |
| L | Directional → RealtimeShadows → RealtimeNoShadows → Baked |
| F9 | Текущий опыт: прогрев 30 кадров, затем 300 измеряемых кадров |
| Backspace | Удалить нагрузку, вернуть исходные освещение и настройки URP |

Стресс-опыты автоматически переходят в CP2. Во время записи запрещены изменение режима, checkpoint и locomotion. HMD-поза не блокируется: держите голову и руки неподвижно, не взаимодействуйте с предметами и не двигайте устройства в XR Simulator. Не меняйте скрипты/пакеты во время измерений. Если открыто меню паузы работы 6, закройте его перед записью. Остановка Play во время записи оставляет помеченный неполный CSV; анализатор не выдаёт его за 300 кадров.

### Где данные и что в них

Каждая запись — отдельная папка `Application.persistentDataPath/Profiling/<UTC-время>`:

- `<имя>.data` — бинарный лог Unity Profiler; при завершении проверяется наличие непустого файла. В обычной Release-сборке бинарное профилирование не обещается: нужен Editor или Development Build.
- `<имя>.csv` — 300 кадров после прогрева; `complete=1` только для законченного захвата. Незавершённые записи не попадают в основные графики.
- `environment.txt` — версия Unity, платформа, GPU/API, разрешение, fixed timestep, Editor/Development.

Profiler.logFile используется через официальный бинарный режим, после записи прежнее состояние Profiler восстанавливается. Уже работающая сторонняя бинарная запись не перезаписывается: сначала завершите её. В .data могут быть дополнительные граничные кадры; в Profiler выберите одинаковые **300 полных кадров** обеих записей. Маркер `ProfilingCapture.Sample` отмечает измеряемое окно; счётчики читают последнее завершённое значение. Если ваша версия Profile Analyzer требует сохранённый из окна файл, загрузите бинарный лог в Profiler и выполните Save, затем Pull Data в Analyzer. Наличие непустого .data ещё не доказывает число кадров: подтвердите его в Profiler.

CSV содержит frame_ms, CPU Main, Render Thread, GPU, Batches, SetPass, Tris, Verts, GC Alloc/frame, Total Used Memory, Physics.Simulate и число незаснувших тел. Недоступные счётчики — `NaN`/пустые поля Excel, **не нули**. GPU 0 при недоступном тайминге считается N/A. Physics.Simulate — конкретный маркер, не весь модуль Physics. Для значений всего модуля, Total/Self/Calls и GC конкретного метода используйте Profiler. Сами счётчики и UI добавляют небольшую нагрузку; держите её одинаковой во всех опытах.

## Этап 2. Исходная сцена

1. Backspace возвращает режим работы 6, включая исходное состояние SRP Batcher. Deep Profile **выключен**.
2. Поочерёдно 1, F9; 2, F9; 3, F9. Получите `Stage2_CP1.data`, `Stage2_CP2.data`, `Stage2_CP3.data` в разных папках сессий. В Editor Profiler проверьте целевой процесс и включённые CPU/Rendering/Memory; сохраните сами записи, не только CSV.
3. Лист **Этап 2** Excel заполняется из CSV. Подтвердите средние/максимальные значения по выбранному диапазону ≥300 кадров. Used Memory — используемая память, не суммарно зарезервированная.
4. В CP3: CPU Usage → Hierarchy, сортировка Total; выберите 5 самых дорогих строк и заполните **CP3 Top5**. Запишите Total, Self, Calls, GC и пояснение каждой, приложите скриншот. Имена нельзя определить по исходникам. Возможные категории для объяснения: работа скриптов, физика, подготовка рендеринга, ожидания GPU/частоты; это примеры, а не ваши результаты.
5. Сопоставьте Main/Render/GPU в Timeline и бюджет 13,9 мс. Ожидание Present само по себе не доказывает GPU bottleneck: проверьте VSync, target frame rate, XR refresh и Editor. Если GPU timing недоступен, отметьте ограничение вывода; один FPS не устанавливает узкое место.

## Этап 3. Графическая нагрузка

Префаб — **то самое кресло работы 6**, упрощённое Blender до **2993 треугольников**. Происхождение и SHA256 исходника в `profiling-model.json`, лицензия CC0 в CREDITS. Editor собирает его в один Renderer и один материал, нормализует длинную сторону до 0,35 м для компактного стенда. Исходная сцена работы 6 и её размеры не изменены. Позиции детерминированы для каждого N в зоне 20 × 20 м; Static отключён у всех экземпляров. При 2000 объектах исходный workload — около 6 млн треугольников до отсечения/LOD, а фактические Tris берутся из Profiler.

Для открытого обзора в стресс-режиме отключается **рендеринг задней стены и потолка** копии мастерской. Это одинаково для N=0 и всех четырёх серий; Backspace восстанавливает их. Поэтому Stage3 N=0 — собственная контрольная точка этой серии, а не идентичный Stage2 CP2. Фрустум и глубина всё ещё влияют на фактические Batches/Tris.

| Серия | SRP Batcher | Материал.enableInstancing | LOD |
|---|---|---|---|
| Baseline | off | off | LOD0 принудительно |
| SRPBatcher | on | off | LOD0 |
| GPUInstancing | off | on | LOD0 |
| LOD | off | off | автоматический LOD0/LOD1/LOD2/Culled |

Dynamic Batching не используется: его API настройки в URP 17.6 удалён как устаревший. Для Instancing используются общий Mesh/Material; SRP выключен, чтобы он не имел приоритета над инстансингом. LOD1/2 — кубические proxy (дешёвые заменители с потерей формы), не обещание одинакового качества. При выключении LOD остаётся только LOD0, а не три меша сразу. Для освещения используется отдельный подготовленный в редакторе URP preset: исходный asset мастерской не изменяется; после опыта восстанавливаются прежние QualitySettings.

1. 0 → F9 даёт Baseline N=0. Затем N → F9 для 100/250/500/1000/2000. После смены режима дождитесь стабилизации/прогрева шейдеров. Держите Game View и качество одинаковыми.
2. M включает следующую серию; 0 начинает её с N=0, затем повторите остальные N. Всего **24 обычные записи** в CP2. Bad/Good автоматически убираются при возвращении к обычной графической серии.
3. Скопируйте обычные CSV (без Deep Profile) в отдельную папку, затем:

```bash
python3 -m pip install -r Tools/profiling-requirements.txt
python3 Tools/analyze_profiling.py --input /path/to/RegularCaptures --output Artifacts/Profiling_Report.xlsx
```

Лист **Графика**: 4 серии среднее/максимум/Batches/SetPass/Tris/frames, диаграмма mean frame time от N и линия 13,9 мс. **Максимальное N** даёт два ответа: по среднему и более строгий по максимальному кадру. Порог определяется только после всех шести полных N, без интерполяции. Неполная серия не объявляется успешной. Дубликаты: последняя полная запись по времени CSV; сохраняйте исходные файлы и объясняйте повторные прогоны.

Объясняйте эффект по факту: SRP может уменьшить CPU-подготовку, не снизив число Batches; инстансинг объединяет совместимые экземпляры, но зависит от шейдера/состояния; LOD снижает Tris и иногда draw calls за счёт culling, но меняет детализацию. Это гипотезы для проверки, не подставленные результаты.

## Этап 4. Скрипты и GC

1. Backspace; B создаёт 500 объектов, CP2. `BadBehaviour.cs` сохранён с тем же кодом, что в задании: поиск игрока, sqrt-distance, массив+List, строка и доступ .material в Update. В копии сцены игрок имеет **ровно** имя `XR Origin (XR Rig)`, а нагрузочный объект — Renderer на корне. Нулевые ссылки не маскируются изменением плохого скрипта.
2. Deep Profile off; F9 → `Stage4_Bad_CP2.data`. В Hierarchy найдите BadBehaviour.Update и запишите Total/Self/Calls/GC Alloc. В Timeline/GC-графике отметьте GC.Collect и интервал между пиками. Если пиков за 300 кадров нет, это так и запишите, не придумывайте частоту; при необходимости увеличьте `ProfilingCapture.frameCount` для более длинной отдельной записи.
3. Выйдите из Play, включите **Deep Profile** в Profiler, дождитесь готовности и вновь запустите Play: сделайте **одну отдельную** запись B/F9. Храните её .data и CSV отдельно от обычной папки анализа. Найдите самый дорогой вызов. Deep Profile меняет стоимость методов, поэтому его числа не сравниваются с обычным Good. После этой записи остановите Play, выключите Deep Profile и вновь запустите сцену для Good. Это также исключает перенос runtime-кэшей через перезагрузку скриптов.
4. G создаёт те же 500 позиций с GoodBehaviour: ссылки и MaterialPropertyBlock один раз в Awake, sqrMagnitude, нет покадровых List/строк/.material, изменение цвета только при входе в радиус 3 м. Маркер **GoodBehaviour.CheckDistance** охватывает проверку. Как и буквальный Bad, предмет остаётся красным после выхода — самовольного сброса цвета нет.
5. F9 → `Stage4_Good_CP2.data`. Проверяйте **GC Alloc именно метода = 0 B в устойчивом режиме**; это цель реализации, не измеренный здесь результат. Общий GC/frame приложения из CSV не равен GC одного метода. Измерение начала/создания объектов исключается прогревом, как и первоначальные MaterialPropertyBlock.
6. Profile Analyzer → Compare: загрузите обычные Bad и Good (или Profiler Load → Pull Data для каждого). Одинаковые 300 кадров, без Deep Profile. Имена методов разные: читайте реальные строки Bad.Update и Good.CheckDistance; отсутствие одного имени во втором файле не означает «всё ускорилось до нуля». Заполните **Этап 4 метод**, приложите Compare и GC-график.

Bad клонирует материалы при приближении; отдельный компонент освобождает эти копии при удалении нагрузки. Очистка происходит вне измеряемого интервала, а сам плохой код не исправлен.

## Этап 5. Физика и освещение

### Физика

P создаёт **300 Rigidbody с MeshCollider Convex**, O — те же позиции/массы/визуальные меши с BoxCollider. Размеры bounding box одинаковы, диапазон высот 6–11,6 м, Discrete, fixed timestep сохраняется. Для Convex используется явный выпуклый 12-гранный proxy (24 вершины / 44 треугольника), а не сложная render-сетка: это обеспечивает малый hull в пределах ограничений PhysX. Форма контактов отличается от Box, что нужно учитывать в выводах; этот опыт не измеряет cooking полного кресла на 2993 треугольника. Запись падения начинается автоматически с минимальной задержкой после подготовки/кукинга, без 30-кадрового прогрева; приготовление объектов не выдаётся за постоянную стоимость симуляции.

В CSV `awake_bodies` показывает фазу. Падение может закончиться раньше 300 кадров: анализатор отдельно считает средние для строк с awake_bodies > 0 и = 0, а не объявляет смешанное среднее «падением». После полного засыпания нажмите F9 ещё раз для отдельной записи Sleeping. Повторите для второго коллайдера. Проверьте отсутствие ошибок convex cooking/проваливания: повреждённый тест нельзя засчитать.

Лист **Этап 5 физика** показывает число кадров каждой фазы, frame mean и маркер Physics.Simulate. Время **всего модуля Physics** заполните из .data вручную. Проверка сна 300 тел и сами счётчики имеют одинаковую небольшую накладную стоимость в обеих сериях.

### Свет

1. Сначала вне Play откройте профилировочную сцену и выполните **VR Practice → Profiling → Bake lighting for comparison**. Это настоящий `Lightmapping.Bake`, который может занять время. Статичным геометрическим объектам добавляется Contribute GI; динамические Rigidbody/Animator исключаются. Для большой плоскости Ground используется Scale In Lightmap 0.1, чтобы не тратить основную часть запекания на дальний 80-метровый пол; качество floor lightmap нужно учитывать в выводе. Флаг готовности ставится только при успешном Bake и наличии lightmaps.
2. Play, Backspace, 2. L последовательно включает **1 Directional**, **+8 Realtime Point / Soft Shadows**, **те же 8 без теней**, **Baked**. На каждом варианте F9. Четыре исходных точечных светильника работы 6 в этих испытаниях выключены. URP разрешает дополнительные тени и до 8 дополнительных источников на объект, поэтому Soft Shadows не остаётся пустой настройкой компонента.
3. Baked без lightmaps **не включается**, панель сообщает о необходимости Bake. В Baked включаются сохранённые lightmaps, runtime-свет восьми ламп выключен. В остальных случаях baked-карты и lightmapIndex отключены, поэтому запекание не загрязняет исходные серии. При выходе из Play исходные настройки восстанавливаются.
4. GPU/Render Thread, Batches, frame time — в Excel. Если GPU-счётчик недоступен, используйте Render Thread и отметьте N/A; не называйте его временем GPU.
5. Для RealtimeShadows откройте **Frame Debugger**, Enable, разверните shadow passes, посчитайте и сделайте скриншот. Число зависит от видимости/culling, атласа, каскадов и directional-света; «8 ламп × 6 = 48» не подставляется автоматически.
6. По фактическим Physics/CPU/GPU/Render/Shadow данным сравните нагрузку и выберите настройки VR. Не делайте вывод о GPU по общему времени кадра без Timeline/GPU evidence.

## Этап 6. Development Build

1. Нужен модуль **Windows Build Support** для этого редактора. Вне Play: **VR Practice → Profiling → Build Windows Development + Autoconnect**. Команда использует только Profiling_Андижан и флаги Development, ConnectWithProfiler, AllowDebugging. Она проверяет поддержку платформы и итог BuildReport, не сообщает об успешной сборке при ошибке. На время сборки default URP включает preset с дополнительными/мягкими тенями, чтобы нужные варианты не удалялись stripping; исходная настройка восстанавливается в finally. Базовая серия всё равно использует явный preset мастерской. Материал-asset сохраняет instancing-варианты, а его runtime-копия выключает instancing в остальных сериях.
2. Запустите `Builds/ProfilingWindows/VRpractice.exe`. В Profiler выберите подключённый Player; проверьте разрешение/качество и отсутствие других тяжёлых процессов. Наличие бинарника ещё не является проверкой автоподключения.
3. Backspace, затем F9: в standalone исходный режим автоматически выбирает CP3, создаёт `Stage6_Build.data` и CSV stage=6. Не используйте результаты Stage3/4 как исходную сборку.
4. Сравните с Editor Stage2 CP3 в листе **Этап 6**, найдите наличие/отсутствие EditorLoop в Timeline. Editor выполняет дополнительные задачи и может использовать иной рендер-контекст; Development-профайлер тоже имеет overhead. Объяснение должно опираться на записи, а не на предположение, что сборка всегда быстрее.
5. Шлем — необязательный дополнительный опыт: профиль OpenXR/платформа/модули настраиваются отдельно; запишите модель, refresh и реальное eye resolution. Замер ПК не выдаётся за профиль устройства.
